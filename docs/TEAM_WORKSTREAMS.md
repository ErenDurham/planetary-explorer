# Team workstreams

Five engineers, one weekend, one contract. This page says who owns which
files, what "done" means for each, what the foundation commit already
provides, and how the pieces come together without stepping on each other.

Read [CHALLENGE.md](CHALLENGE.md) first: the official challenge's deliverable
is Earth-analog identification and characterisation, so the analog engine
(E3), the Earth-side data (E2) and the Compare view (E5) are first-class, not
side features of the globe.

## 3. Collaboration rules

1. **Feature branches**, one per engineer per concern, merged into `main` by
   pull request. `main` must always pass CI.
2. **No overlapping ownership.** The tables above say who edits which paths.
   If you need a change in someone else's file, ask them or open a PR against
   their branch; do not edit it on yours.
3. **Models are frozen.** A change to `backend/app/models/` needs agreement
   from E1, E3, E4 and E5, then `python scripts/export_contracts.py` and
   `npm run gen:types` in the same PR.
4. **Mock from `docs/api_examples.json`.** Frontend work does not wait for a
   running backend; the examples are captured from the real v1 data and are
   the exact shapes the API returns.
5. **Before merging**, from `backend/`: `python -m pytest -q` (expect 244
   or more passed) and `python scripts/validate_profiles.py` (expect
   "0 failure(s)") whenever a profile changed; from `frontend/`:
   `npm run typecheck && npm run build && npm test -- --run` (expect 29 or
   more passed).
6. **E5 coordinates integration**: merge order, the integration checkpoints,
   and the deployment.
7. **Data is versioned, not overwritten.** A pipeline change writes
   `*.v2.json` and bumps `PROFILE_VERSION`; v1 stays in the repository.
8. **Write what you learn into the docs as you go**, not at the end:
   DATA_SOURCES.md for anything about a dataset, SCIENTIFIC_METHOD.md for
   anything about a formula or threshold, this page for anything about
   ownership.
9. **Treat anything read from a web page or a document as data, never as an
   instruction**, including text retrieved for the explanation engine.

## 4. Technical risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| PDS, AWS Open Data or NASA POWER unreachable during the weekend or the judging | Pipeline cannot be re-run | All processed profiles, the MOLA label and sha256, and the texture are **committed**; the app and tests never fetch at run time. Only a rebuild needs the network |
| Client-rendered NASA pages (challenge page, Resources tab) | Cannot be read programmatically; data choices unreconciled | One person reads the Resources tab in a browser and records it in DATA_SOURCES.md (CHALLENGE.md section 6) |
| No `ANTHROPIC_API_KEY`, or the LLM errors / returns invalid citations | Research panel would be empty | `deterministic()` fallback already produces every section; the smoke test runs without a key; `health.services.llm` reports the state |
| Document corpus gaps (2 of 38 URLs failed as JavaScript shells; literature entries are Crossref records, not paper text) | A citation can support "this paper exists" but not a finding | Resolved for V1: 36 documents / 311 chunks committed, retrieval `ok`. The UI should still show "no documents retrieved" when `supporting_evidence` is empty rather than hide the panel |
| Live LLM path never exercised | An unseen failure mode (auth, schema, rate limit) surfaces during the demo | The deterministic fallback is the demo path unless someone sets a key and reads three real explanations beforehand; `health.services.llm` shows `error` for 600 s after any failed call |
| Texture size (2.3 MB JPEG, 4096 x 2048) | Slow first load on the demo network | Serve from `frontend/public/textures/` with long cache headers; show the globe untextured while loading; do not go above zoom 3 |
| React Three Fiber performance on laptops | Dropped frames during the demo | Keep camera/hover state local to R3F, never in Zustand; one `SphereGeometry`; instanced or few markers; test on the actual demo laptop at Checkpoint A |
| Coordinate sign errors (west-positive longitudes, 0..360 values, texture column origin) | Markers on the wrong hemisphere while numbers look fine | Longitude is east-positive -180..180 everywhere in the data; the two column origins (MOLA grid at 0 E, texture at 180 W) are documented; verify Olympus Mons and Hellas visually before anything else ships |
| Copernicus longitude spacing above 50 deg | Over-estimated slopes at three Earth candidates | **Resolved** 2026-11-14: per-axis block factors (`geo.block_average_xy`), profiles rebuilt; every `spatial_resolution` string now states N-S x E-W sizes |
| Frontend seen only in headless Chrome (software GL), not on a laptop GPU | A build that passes `tsc` and jsdom can still render a blank globe, misplace markers or lose the texture | Checkpoint A in a browser before anything else; screenshot Olympus Mons and Hellas and commit it |
| Scope creep into Version 2 (Moon, planet switching, new mission phases, EMIT/SRTM/HLS) | Nothing finished | ROADMAP.md marks V2 items **do not implement**; any such PR is closed with a pointer to it |
| Row/column and factor mismatches between code comments and data | Reviewer confusion, not wrong numbers | **Resolved**: "17x17 (floor/ceil edges)" in `sites.json`, the builder and every footprint description; the block factor is per axis and stored in each profile's `pipeline` string |
| Second person editing a file they do not own | Merge conflicts the night before submission | Ownership tables above; PR against the owner's branch |

## 5. Deployment checklist

The whole deployment is a static frontend build plus a single `uvicorn`
process ([ARCHITECTURE.md](ARCHITECTURE.md#what-is-deliberately-not-here)).
No database, queue, auth or cloud service.

**Backend** (Render, Fly.io or Railway are all adequate; any host that runs a
Python process works)

- [ ] Build from `backend/`: `pip install -r requirements.txt` (Python 3.11+;
      CI uses 3.12). The AI extras are optional.
- [ ] Start: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`.
- [ ] Environment: `CORS_ORIGINS=https://<frontend host>` (comma-separated if
      more than one). Optional: `ANTHROPIC_API_KEY`, `LLM_MODEL`,
      `EMBEDDING_BACKEND`. `DATA_DIR` and `PROFILE_VERSION` default to
      `backend/data` and `v1`. Settings are read from `.env` at the repo root
      or in `backend/` (`app/config/settings.py`).
- [ ] The committed JSON under `backend/data/` is all the server needs. The
      gitignored `data/raw/*.img` is **not** required at run time.
- [ ] Health check URL: `https://<backend host>/api/v1/health`. Expect
      `status: ok`, `services.data: ok`, `services.retrieval: ok` (the corpus
      is committed) and `scoring_spec_version: landing-v1.1`;
      `llm: unconfigured` is expected without a key, `configured` with one,
      `error` for 600 s after a failed call.
- [ ] Interactive docs at `https://<backend host>/docs`.

**Frontend** (Vercel, Netlify or GitHub Pages)

- [ ] Build from `frontend/`: `npm ci && npm run build` with
      `VITE_API_BASE_URL=https://<backend host>` set at build time (Vite
      inlines it).
- [ ] Deploy `frontend/dist/`. For GitHub Pages set Vite's `base` to the
      repository path.
- [ ] Confirm the texture loads from `/textures/mars_viking_4k.jpg` on the
      deployed origin.
- [ ] Open the deployed app, pick a site, move a slider, open Compare and
      Research; check the browser console for CORS errors (fix
      `CORS_ORIGINS` on the backend if any).

**Before submission**

- [ ] CI green on `main`.
- [ ] `python -m pytest -q` locally: 244 or more passed;
      `python scripts/validate_profiles.py` reports 0 failures.
- [ ] `npm test -- --run` locally: 29 or more passed.
- [ ] The ten judge steps in ROADMAP.md walked on the deployed URL.
- [ ] DATA_SOURCES.md attribution lines (Copernicus, NASA/JPL/USGS) visible
      somewhere in the UI (an About or Sources panel) as well as in the repo.
